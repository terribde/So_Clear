# 架构决策记录

状态说明：以下ADR为**设计基线v0.6，尚未实施**。五组/匿名认证采用ADR-014/015，后端缓存每日写Supabase采用ADR-016（用户已明确方向/服务商）。可信proof/平台凭据、数据权利/地域/预算/实例仍须P0验证。待确认项见[01](01-product-and-scope.md)，变更同步接口/权限/数据/验收。

## ADR-001 模块化单体与独立后台进程

问题：首期需兼顾清晰边界、查询峰值和可维护性，过早拆微服务增加运维与一致性成本。

决策：单仓TypeScript，React/Vite前端统一apps/web，Fastify模块化API、普通worker和平台ai-worker独立。管理页面同站/admin、独立严格CSP文档；同源入口将管理API分流到独立内网部署，后端凭据不合并。AI三模式和command-runner按能力隔离，contracts仅纯协议；跨域走port/编排/outbox。v0.3以ADR-013替代旧独立管理域名方案。

代价：数据库仍是共享故障域，公开 API 与写入需并发预算隔离。升级条件：某域有独立吞吐、故障或团队边界且测得收益，再拆部署；不因代码文件多就拆服务。

## ADR-002 业务数据只经 BFF，Supabase 非公开基础表

问题：隐藏前端 SDK 或后端 DTO 不能阻止用户直连获授权的基础表，可能绕过限流并读出隐私列。

决策：Supabase 提供 Auth/PostgreSQL，业务 SQL 只在后端。关闭不用的 Data API，并保持业务 schema 不暴露、最小 grants/default privileges 与 RLS。普通运行时无 owner、BYPASSRLS、service-role。直接 SQL 事务内设置受信任身份上下文，数据库重查权限。

代价：需要维护 API、低权限角色、事务上下文和池化测试；RLS 不能防完整后端失陷。若以后需要外部 Data API，先单独建受控公开面、请求准入与安全验收，不能复用基础表授权。

## ADR-003 不透明 Cookie 会话

问题：旧白板建议浏览器 Bearer Supabase JWT，浏览器令牌暴露面与多端鉴权一致性需要统一处理。

决策：BFF保管Supabase令牌，浏览器用HttpOnly/Secure/__Host-应用会话；本站写入CSRF/Origin。管理员在同域使用另一个绑定应用session/当前授权版本的短时升权Cookie与MFA，按ADR-013执行，不把同源Cookie/路径当XSS隔离。学生模型Key独立，仅当前页内存，进入管理文档前清理。

代价：需安全会话存储、刷新轮换、CSRF 与可用性设计。原生客户端若需要 Bearer，单独设计凭据范围和存储，不能让同一路由随意混合认证模式。

## ADR-004 公开字段投影与身份分离

问题：RLS 只过滤行，公开整行仍可能暴露学生/审核者关联字段；前端不展示不等于不可读取。

决策：评价作者只映射独立平台账号，公开投影/DTO无稳定作者关联；内容管理员无身份映射读取权。精确评分贡献留core，公开摘要按阈值输出。系统管理员仅能按目的/scope核查平台行为，不提供校园实名揭示或tag反查。学生认证另按ADR-015零校园原文持久化；不承诺绝对不可关联。

代价：多一层投影与修复任务，需跨导出/日志/AI检查。新增公开字段须评审可关联性和来源权利。

## ADR-005 缓存按内容敏感性分级

问题：查询要高吞吐，同时撤稿不能因旧 CDN/Redis 内容长时间继续公开。

决策：目录/评分摘要可共享缓存；正文、学生AI证据与平台教师总结 HTTP no-store，无 CDN/Service Worker/持久化浏览器缓存。正文/证据/平台派生总结交付每次向主库权威状态验版本；来源集变化同步提升总结epoch。提交后新授权读取不可获得旧正文/旧总结；已授权在途响应与已下载/外发内容不保证收回。

代价：正文读取有主库检查成本，需要独立限流/连接预算。后续如尝试 CDN 正文，必须先证明等价撤稿承诺与故障 fail closed，否则保持当前方案。

## ADR-006 游标分页与有限查询

问题：深 offset、每次精确 count、全量 Hash→内存分页和任意排序会放大数据库/Redis负载。

决策：SQL 有界查询、稳定排序、签名 cursor，包含查询摘要与数据版本；总数按需缓存/估算。未知时间、评分和歧义映射显式表示。

代价：用户不能任意跳到第 10000 页，数据版本切换需重新查询。对后台确需全量数据的操作提供受控异步导出。

## ADR-007 事务 outbox 与绝对贡献投影

问题：数据库提交后 Redis 发布可能失败；至少一次事件会重复或乱序，单纯 delta 去重会漏算。

决策：业务事务写 outbox，worker 租约领取；每评价保存最后已应用版本和绝对贡献，锁定后减存量加目标，低版本忽略。定期按一致快照/水位校准，内容撤除同步发生。

代价：有投影滞后、租约/死信/校准运维成本。新增独立消息系统只在数据库 outbox 吞吐或跨系统需求证明必要后引入，事实账本仍不能只放 Redis。

## ADR-008 AI 分层与受限数据能力（v0.2 替代旧统一执行方案）

问题：学生希望使用自己的供应商与模型；平台模型需独立服务评价分析与教师总结，不能混用密钥、数据和费用。

决策：学生模型解析/解释在浏览器执行，平台仅提供受限 DSL、确定性候选、公开证据和当前状态验证。学生无本站模型job/预算账本/SSE。平台分析独立持久作业、供应商Key、费用预留、全局并发与对账，只做脱敏评价分析和有据教师总结，不开放SQL/网页工具。两个链路使用独立adapter与权限。

代价：客户端可被学生修改，本站只能控制自己的数据接口，不能保证学生供应商账单或把个人模型解释认证为平台结论。平台总结有生成滞后，失效期间显示暂不可用；普通查询保持独立。

## ADR-009 首发聚焦教师、课程与评价治理

问题：照搬旧系统所有域会延缓安全和基础查询交付。

决策：积分、签到奖励、评价奖励与AI扣分正式取消，无延期恢复或隐藏开关。通知抓取、捐赠、实时抢课、教师人事评价和教室评分不在首发。学生grant撤销/账号受限不取消本人撤回、申诉与删除请求能力。

代价：不建设积分激励；后续泛校园需求另行决策，不能据旧参考项目自动恢复积分。改变评分维度、样本阈值或防重范围要新增产品 ADR，并设计历史口径迁移。

## ADR-010 容量目标必须由负载与故障证据支持

问题：“全体学生可用”“接 Redis”“serverless”均不能推导吞吐、费用或可用性。

决策：明确在线人数、到达率、请求分布、缓存命中、DB池、AI槽位与费用模型；采用开放到达率混合压测，覆盖冷缓存、长尾和故障。指标以 [06](06-capacity-and-performance.md) 为唯一数值基线，环境/供应商额度未验证时不承诺容量。

代价：需压测环境与成本、目标学生网络实测；容量不足通过限额/灰度保护系统，再按瓶颈扩容。

## ADR-011 学生 Key 仅浏览器直连（用户明确选择）

问题：页面需支持学生输入供应商、Key与模型名，必须决定凭据是否经过本站。

决策：学生Key仅当前页内存，由浏览器向注册表精确HTTPS目标发送；本站不接收、存储或转发，不提供服务端/第三方代理回退。无本地持久保存、URL Key、自动上传验证和诊断日志。供应商需真实浏览器CORS兼容，失败时提示更换供应商。前端Key配置与本站Auth客户端完全隔离。

代价：部分供应商不能在此模式工作；刷新需重填；XSS、浏览器扩展或已外发资料不能靠本站完全控制。平台只控制自己检索API，不承诺替学生控制计费。详见 [12](12-student-byok-ai.md)。

## ADR-012 平台置信度为审核辅助，教师总结为可撤稿派生内容

问题：模型不能凭文字断言评价真伪；派生总结可能间接保留已撤回评价信息。

决策：评价置信等级针对证据强度/具体性/内部一致性，初版不输出未校准真伪概率、不改原分、不自动审核、不加权教师总分。教师总结仅当前published且达到样本阈值，记录完整来源manifest和epoch；任意来源集变化同步失效，提交与读取都主库gate，正文no-store。后台生成有独立预算和版本化质量评测。

代价：总结失效到重新生成期间不可用，置信度需人工解释与申诉；不能把低分、少数意见或不熟练表达自动当作不可信。详见 [13](13-platform-ai-analysis.md)。

## ADR-013 所有管理功能接入同站工作区，后台按权限隔离

问题：用户要求平台全部管理功能在前端站点中可见可控，且仅管理员可操作；旧apps/admin/独立管理域名方案与此不符。

决策：同一apps/web工程用学生index.html与管理admin.html双文档入口，/admin服务端先检查当前管理资格，再在严格CSP最小页完成MFA升权。管理入口/模块/动作按capability+scope显示；每请求、intent确认、作业执行/提交都重查当前授权。普通BFF无管理凭据，同源反代将/api/v1/admin分流admin-api，security/ops/secret-write runner只执行固定工作流。审核、数据、AI、授权/隐私、运维恢复发布等均有站内页面和结果审计。

代价：前端同源共享浏览器信任域，普通页面XSS可能发同源管理请求；严格管理文档不能当跨origin隔离。全站XSS防护、完整导航、清BYOK、短时升权、动作确认与后端权限同时成立。平台密钥仅write-only轮换；学生Key边界不变。初始两名system_admin引导/灾难break-glass属受审计基础设施恢复，无匿名管理自举。

验证：完整功能/权限覆盖矩阵、非管理员直访、跨capability/学校/对象、MFA/CSRF、角色撤销、队列延迟后失权、intent调包、bfcache/切账号泄漏、Cookie转发和admin CSP独立生效；参考 [14](14-admin-workspace-and-security.md)。

## ADR-014 固定五权限组，管理职责与学生资格正交

日期：2026-10-18。状态：采用，待实现。

决策：唯一用户主分类为system_admin、content_admin、verified_student、user、guest。mainGroup单值，管理两组显式授权且互斥，其他已登录账号按独立active学生grant派生，未登录游客不落持久组。无数字等级继承；capability/scope只能在组允许集合内缩减，内容组不能加系统cap变相提权。系统组逐动作授权而非DB owner，管理员学生专有行为也须独立grant。工作负载/SQL角色不增加用户组。

验证与代价：更新01/04/05/08/14的矩阵与负测；保护最后有效system_admin、初始化至少两名支持明确高敏复核；管理组切换同事务防双组，未知组/cap默认拒绝。旧六角色模板不迁入新权限体系。

## ADR-015 学生认证零原文、HMAC集合防重、单事务授予

日期：2026-10-18。状态：采用，待实现。完整协议见[15](15-anonymous-student-verification.md)。

问题：低熵学号MD5/裸hash可被枚举；存学校材料、校园SSO到Auth、tag↔user表会扩大真实身份关联。必须防并发重复领取，也不能先烧标签再异步发券损失资格。

决策：独立student-verifier验证可信学校proof，学校原文/凭据/subject/token/材料及密文仅获准内存暂态，不进Supabase身份、DB、日志/采样、对象/队列或备份。固定域/学校/canonical namespace/稳定subject确定编码，用隔离KMS的完整HMAC-SHA-256标签查重；多issuer统一身份，不提供学号MAC oracle。查重集合仅keyVersion+tag，无平台账号/时间关联列；平台grant无tag/校园身份。受控单PG事务锁keyring/账号/challenge，查全历史tag、插当前唯一tag+建grant+消费challenge；响应丢失查原账号grant。

代价：只证明首次验证时学生，无自动到期/续证/新账号换绑；删号/撤销不释放spent tombstone，原账号只凭平台恢复凭据补救，不能凭学号反查。无稳定同人subject时保证限于同一权威学生身份一次；同事务WAL/xmin/时序与完整服务失陷仍可能关联，不能宣称密码学不可关联。未来持续在校验证须新ADR和成熟协议，不偷加tag-user映射。

轮换/恢复：由于无原文不能离线重算旧tag；每次检查全部覆盖历史消费的Key版本，仅写当前版本，轮换与claim按keyringGeneration线性化。历史Key丢失/泄漏、tag恢复水位不完整则关闭新认证；通用业务15分钟RPO不能允许丢失已消费tag。无管理员清表/强授/真实身份揭示例外。

验证：对照15做proof真实性/规范化、双账号与同账号不同身份并发、keyring切换、提交前失败/响应丢失、删除撤销/恢复；canary遍历全部持久出口，缺历史Key或恢复缺口时fail closed。P0前置未通过只用合成数据，不先收校园原文等待以后匿名化。

## ADR-016 后端统一数据库缓存，每日将缓存写入Supabase

日期：2026-10-18。状态：采用，待实现；用户明确“后端每日将缓存写到Supabase”，替代此前待选缓存服务商/方向的假设。默认落点是同项目Supabase PostgreSQL非公开cache_persistence快照表，详见[16](16-backend-cache-and-daily-sync.md)。本ADR补充ADR-005，不降低撤稿/安全承诺。

决策：后端cache-management是键/版本/容量/TTL/刷新失效/每日写Supabase的唯一策略源，前端仅当前页状态，无数据库/缓存SDK或持久副本。数据库JSON浏览器no-store，CDN仅在验证共享边缘与浏览器不存分离后启用，否则后端Redis/限额回源并重测。

cache-sync默认Asia/Shanghai每日03:00一个获准项目环境/scope/日期槽位；从后端运行缓存读取固定版本白名单目录，缺块/过期先限额重建。序列化分批短事务写cache_persistence.snapshots/snapshot_chunks staging，完整schema/计数/摘要/有界SQL回读验证后，同Supabase短事务标ready、CAS切private.cache_snapshot_manifests指针并记job成功；fence/日唯一拒绝重复和旧任务。评分/正文/总结/registry、私有账号/授权/grant/安全/费用/查重、校园原文/tag/秘密排除。

权限/代价：cache_persistence不暴露Data API，撤PUBLIC/anon/authenticated/default grants并RLS默认拒绝；后端adapter用独立最小SQL身份/窄port，无owner/BYPASSRLS/service-role，不修改业务事实表。只作重启预热，最大源年龄暂定30小时，加载前复验当前版本和30/60秒预算；未知失败先查原job/分片，旧fence/半包不激活。业务实时落库，权限/撤稿不等次日。快照与事实表同故障域，不是PITR/查重恢复或独立灾备；每日批写新增DB连接/IO/WAL/存储，需限额/旧版本清理。system_admin可同站按cap/scope管理状态/原日补跑，无前端SQL凭据。

验证：后端缓存→Supabase方向、前端/Data API拒绝、窄SQL角色、固定缓存版本/缺块/混版本、批写超时/提交unknown、损坏分片/完整激活、旧fence/超龄/清理加载竞态、私有canary与峰值预算。具体项目环境/角色迁移、计划时刻/允许年龄/批大小与保留上限实施前固定；当前没有真实写入任务。
